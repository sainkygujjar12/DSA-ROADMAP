# Free deployment and live updates

Use **Render Free + your existing MongoDB Atlas cluster + Brevo HTTPS email**.
The React build and API run together on one Render Docker web service. This avoids
cross-origin API configuration and keeps deployment to one service.

The repository includes `render.yaml`, a non-root Dockerfile, and GitHub Actions
checks. Creating a Render service and connecting the repository are still required;
local files do not activate a cloud deployment or a GitHub workflow.

## What free hosting means

Render Free sleeps after 15 minutes without incoming traffic; waking can take
about a minute. It has monthly usage limits, can restart, and cannot scale beyond
one instance. It also blocks outbound SMTP ports 25, 465 and 587. The Blueprint
therefore uses Brevo over HTTPS instead of Gmail SMTP. Brevo Free currently allows
300 emails per day, shared by verification, resends and password resets. Monitor
this quota: queued emails may arrive after a verification code expires.

This is an economical starting point for a small community. It is not a guarantee
of always-on service or capacity for 200 simultaneous users. Test the deployed
service before a coordinated launch. Do not use fake traffic to defeat idle sleep.

Sources: [Render Free](https://render.com/docs/free),
[Brevo limits](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan).

## One-time setup

1. Push the complete application changes to your GitHub repository
   `sainkygujjar12/DSA-ROADMAP`. Ensure **Validate application / checks** passes.
   Never push `.env` files. GitHub Actions needs to be enabled for the repository.
2. Create a free Brevo account, activate transactional email, verify your sender,
   and create an API key. Follow its sender/domain authentication requirements.
   Store the key in Render, not in frontend variables or GitHub source files.
3. In Render, choose **New > Blueprint**, connect the GitHub repository, and select
   `main`. The included `render.yaml` selects Docker, Free, Singapore, `/api/health`,
   and **After CI Checks Pass**. Use a region close to your existing Atlas region;
   change `region` before creating the service if needed.
4. Fill in the values below. `CLIENT_URL` must be the actual Render HTTPS origin
   (or your own domain), with no trailing slash/path. If Render assigns a different
   subdomain, update it before retrying the first deployment.
5. In Atlas Network Access, allow the service's **outbound IP ranges** shown in
   Render, plus your development machine's IP if required. Avoid permanently
   allowing `0.0.0.0/0`. Use an Atlas database user scoped to the application DB;
   Render receives this credential, not your Atlas account password.
6. Before the first production start, run `npm run db:indexes` from `server/` on
   your machine with the intended database configured. It adds declared indexes
   and never drops indexes or recreates collections. Production disables automatic
   index creation. This command was already run against the current project DB.
7. If using Google login, register the exact deployed origin in Google Cloud's
   **Authorized JavaScript origins**, and use the same client ID in both variables.
   Rebuild when `VITE_GOOGLE_CLIENT_ID` changes; frontend variables are build-time.
8. Deploy and check `/api/health`, then registration, verification, login, password
   reset, saving progress/notes, and refreshes of `/settings` and `/admin`.
   Real email delivery and deployed Google login must be verified here.

| Render variable | Value |
| --- | --- |
| `MONGO_URI` | Your Atlas application connection string, including the DB name |
| `MONGO_MAX_POOL_SIZE` | `20` initially; measure before increasing |
| `JWT_SECRET` | Generated by the Blueprint; keep stable across deployments |
| `CLIENT_URL` | Actual `https://YOUR-SERVICE.onrender.com` origin |
| `TRUST_PROXY_HOPS` | `1` for direct Render proxy; revisit if adding another proxy |
| `EMAIL_PROVIDER` | `brevo` |
| `BREVO_API_KEY` | Private Brevo API key |
| `EMAIL_FROM` | Verified sender address, such as `you@example.com` (address only) |
| `GOOGLE_CLIENT_ID` | Google web client ID, or leave blank to disable |
| `VITE_GOOGLE_CLIENT_ID` | Same client ID, or blank |

Do not seed on every deploy. The current database already contains the catalog.
Render Free has no dashboard shell or pre-deploy commands; run explicit database
maintenance locally with the intended connection configured.

The server checks the current verified email on every authenticated request;
changing local storage, a JWT role claim, or another account's stored `role`

Normal registration cannot choose a role. The admin user list cannot promote
other accounts or delete the owner account.

Your existing verified account has been promoted in the current project DB.
Refresh or sign in again and open `/admin`. For another database, register and
verify this same email normally. Its permissions take effect automatically.
`npm run admin:promote` synchronizes the stored role if needed and refuses any
other email or an unverified account. No password or verification bypass is added.

## CI/CD for changes while the site is live

The flow is:

`feature branch -> pull request -> checks -> merge to main -> Render build -> health check -> traffic switch`

GitHub checks run frontend lint/build, seven browser regressions, server/security
tests, real MongoDB concurrency tests against an isolated CI MongoDB service,
dependency audits, and a Docker image build. Superseded runs are cancelled and
failed browser traces are retained for seven days. CI never needs production DB
credentials, the email API key or the production JWT secret.

Configure a GitHub branch rule/ruleset for `main`: require pull requests and the
`checks` status before merging, and prevent force pushes/deletion. Avoid blanket
branch filters that skip checks; Render requires successful checks for the new
commit. `autoDeployTrigger: checksPass` in `render.yaml` is the CD gate—no secret
deploy-hook URL is needed. Check this setting in Render after importing.

Render builds the new version while the previous version serves requests. Its
health check must pass before the new version receives traffic. Keep schema
changes backward compatible while old and new instances briefly overlap.
Never rename/remove database fields in the same release that first replaces them.
Code rollback does not roll back database changes: take a backup before migrations.

For a failed release, use Render's deployment history to roll back to the last good
version and revert the bad Git commit. Pause automatic deployments while diagnosing
if needed. Free-plan sleep, restarts and usage exhaustion can still interrupt users.

Sources: [Render deploy behavior](https://render.com/docs/deploys),
[Blueprint settings](https://render.com/docs/blueprint-spec),
[health checks](https://render.com/docs/health-checks).

## MongoDB reliability and recovery

Implemented in the app:

- One reusable connection pool per process, capped at 20 sockets by default;
  bounded connection/queue/socket/query waits and no indefinite Mongoose buffering.
- Retryable database writes with majority acknowledgement. Progress changes use
  optimistic concurrency with bounded conflict retries, keeping question sets,
  counters, notes and activity together. Concurrent first visits use a unique-user
  upsert instead of racing document creation.
- Topic/company/sheet question indexes. Run `db:indexes` explicitly for new DBs or
  future index changes; no destructive `syncIndexes` or seeding on startup.
- Readiness reports 503 when the database disconnects. Startup waits for MongoDB;
  SIGTERM drains requests before closing the database connection.
- Per-account authenticated API limits and per-email authentication limits, with
  a separate coarse network guard so a shared Wi-Fi network is not limited to
  20 people signing in. These in-memory limits target one process; they reset on
  restart and are not shared during a rolling deploy. Add a shared limiter store
  before running multiple persistent replicas.

In Atlas, monitor storage, connections, query latency and available resource
metrics. Enable the alerts supported by your tier and an email notification
channel you actually check. Review Render errors/memory/response latency after
releases. Health checks confirm connectivity, not full application correctness.

**Backups are still required.** Atlas Free/M0 does not include managed Atlas
backups. Install MongoDB Database Tools and keep regular encrypted `mongodump`
archives outside the app host. Use a private config file (`chmod 600`) containing
`uri: "YOUR_ATLAS_URI"`, rather than putting a password in shell history:

```sh
mongodump --config /private/path/mongodb-backup.yml --archive /private/path/dsa-backup.archive.gz --gzip
```

Keep that config and archives outside Git. Encrypt archives before storing them
in private off-machine storage; they include users, password hashes and notes.
Schedule backups to match how much progress you can afford to lose (for example,
daily), and back up before catalog migrations. Periodically restore into a separate
test database and check users, sheets and progress. Never test restores over the
live DB. Paid Atlas tiers offer managed backup choices; enable the appropriate
policy if upgrading. No backup schedule has been activated by this code change.

Sources: [Atlas backup availability](https://www.mongodb.com/docs/atlas/backup-restore-cluster/),
[mongodump configuration](https://www.mongodb.com/docs/database-tools/mongodump/),
[Render outbound IPs](https://render.com/docs/outbound-ip-addresses).

## Local verification and limits

From `client/`: `npm ci`, `npm run lint`, `npm run build`, then
`PLAYWRIGHT_CHANNEL=chrome npm run test:ui` (or install Playwright Chromium).
From `server/`: `npm ci`, `npm test`.
For database concurrency checks, set `TEST_MONGO_URI` to an isolated test database
and run `npm run test:integration`. Tests remove only their generated fixtures;
they never read `.env` implicitly or clear existing collections.

The local Docker engine was unavailable, so the image build must pass in GitHub
CI before deployment. Browser tests use API fixtures. Shared-IP tests prove the
rate-limit behavior, not 200-user hosting capacity. Actual deployed load, email
quotas, OAuth setup, backups and recovery still require operational verification.

## Catalog maintenance

Do not run `npm run seed` on an existing database: it recreates catalog collections.
Use the additive `npm run seed:companies` and `npm run seed:sheets` commands.
Preview sheets with `npm run seed:sheets -- --dry-run`. The complete collections
contain 448 original Love Babbar rows and 191 classic Striver SDE rows; repeated
rows share progress. See `server/src/data/curatedSheets/README.md` for provenance.
